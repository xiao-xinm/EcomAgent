## 1. 架构总览

系统采用五层分层架构，层间通过明确定义的接口通信，依赖方向自上而下，上层可调用下层服务，下层不感知上层。

```
┌──────────────────────────────────────────────────────────────────┐
│  Layer 5: 用户触点层 (Touchpoint)                                │
│  APP-H5 / H5网页 — WebSocket + REST                             │
├──────────────────────────────────────────────────────────────────┤
│  Layer 4: 接入网关 / 会话管理层 (Gateway)                         │
│  消息标准化 → 会话管理 → 限流 → 路由到 Agent Core                 │
├──────────────────────────────────────────────────────────────────┤
│  Layer 3: AI Agent 核心层 (Core)                                 │
│  NLU → DM → Skill Router → Risk Router                          │
│  流水线式处理，模块间通过内部事件总线解耦                            │
├──────────────────────────────────────────────────────────────────┤
│  Layer 2: 后端支撑层 (Backend)                                   │
│  电商业务API适配 → 工单服务 → 知识库/RAG → 通知服务               │
├──────────────────────────────────────────────────────────────────┤
│  Layer 1: 基础设施层 (Infrastructure)                            │
│  Redis Cluster │ Milvus │ ES │ RocketMQ │ MySQL │ Prometheus    │
└──────────────────────────────────────────────────────────────────┘
```

### 各层交互关系

| 调用方 | 被调方 | 通信方式 | 说明 |
|--------|--------|----------|------|
| 触点层 → 网关层 | WebSocket / REST | 用户消息上行、Agent 回复下行 |
| 网关层 → Agent核心 | gRPC（同步）/ RocketMQ（异步） | 请求分发、结果回传 |
| Agent核心 → 后端支撑 | HTTP/HTTPS | 技能API调用、知识检索、工单操作 |
| 后端支撑 → 基础设施 | 各组件原生SDK | 数据读写、消息收发 |
| 网关层 → 基础设施 | Redis SDK | 会话状态、限流计数 |
| 坐席工作台 → 网关层 | WebSocket + REST | 工单通知、审批操作 |

### 设计原则

1. **故障隔离**：每层可独立降级，Agent Core 不可用时网关直接转人工
2. **数据安全**：敏感数据不出 Agent Core 内网，API 调用走内网 + mTLS
3. **可观测性优先**：全链路 trace_id 贯穿五层，每层关键指标可独立监控
4. **渐进式降级**：LLM 不可用 → 规则引擎兜底；规则引擎不可用 → 转人工兜底

## 2. 核心模块设计

### 2.1 接入网关设计

#### 2.1.1 消息标准化

所有渠道消息在网关层统一转换为标准消息体，屏蔽渠道差异：

```
原始消息 → 渠道适配器 → 标准消息体 → Agent Core
```

**实现方案**：

- 采用策略模式，每个渠道实现 `ChannelAdapter` 接口
- 标准消息体使用 Protobuf 定义，JSON 作为线上序列化格式
- 适配器负责：渠道特有字段映射、附件下载与转存、设备信息提取

**渠道适配器接口定义**：

```java
public interface ChannelAdapter {
    StandardMessage normalize(ChannelRawMessage raw);
    ChannelResponse denormalize(AgentReply reply, String channel);
    boolean supports(String channel);
}
```

**消息校验**：进入标准化流水线前做 JSON Schema 校验（使用 `networknt/json-schema-validator`），校验失败直接返回 `1001` 错误码，不进入后续流程。

#### 2.1.2 会话管理

**会话生命周期**：

```
创建 → 活跃(30min TTL) → 超时关闭 → 冷存(24h可恢复) → 归档
```

**实现要点**：

- **会话存储**：活跃会话存 Redis Hash（key: `session:{session_id}`），字段按需读写
- **会话索引**：维护 `user_sessions:{user_id}` → Set<session_id>，保证同用户同渠道单活
- **单活保证**：新建会话前检查是否已有活跃会话，若有则关闭旧会话再创建新的
- **会话恢复**：关闭后 24h 内的会话数据保留在 Redis（TTL=24h），用户重连时按 user_id 查询最近会话并恢复
- **上下文窗口**：对话轮次保留最近 20 轮，超过时 FIFO 淘汰，使用 Redis List 的 `LPUSH + LTRIM` 实现

**会话状态同步**：每次对话状态变更时，通过 RocketMQ 发送 `SessionStateChangeEvent`，下游工单服务、监控服务消费。

#### 2.1.3 限流

采用 **令牌桶 + 滑动窗口** 双维度限流：

| 维度 | 算法 | Redis 实现 | Key 格式 |
|------|------|-----------|----------|
| 单用户 QPS (10/s) | 滑动窗口 | `INCR` + `EXPIRE` | `rate:qps:{user_id}` |
| 单用户日限额 (500/d) | 计数器 | `INCR` + `EXPIRE`(次日0点) | `rate:daily:{user_id}` |
| 渠道总 QPS (1000/s) | 令牌桶 | Lua 脚本实现令牌桶 | `rate:channel:{channel}` |

超限响应：HTTP 429 + `{"code":4004,"message":"操作过于频繁，请稍后再试"}`

限流在 Filter 层执行（Spring Cloud Gateway GlobalFilter），顺序在鉴权之后、路由之前。

### 2.2 NLU 模块设计

#### 2.2.1 意图识别 Prompt 设计

采用 **Few-shot + CoT** 的 Prompt 架构，通过 LLM Function Calling 获取结构化输出：

```python
INTENT_PROMPT_TEMPLATE = """
你是一个电商客服意图识别引擎。根据用户输入，识别其意图和实体。

## 意图列表
{intent_list}

## 输出格式
请以 JSON 格式输出：
{{
  "intent": "意图编码",
  "confidence": 0.0-1.0的置信度,
  "entities": [
    {{"name": "实体名", "value": "实体值", "source": "extracted|context|default"}}
  ],
  "reasoning": "识别推理过程（简述）"
}}

## 上下文信息
当前意图: {current_intent}
已填槽位: {filled_slots}
历史对话: {dialog_history}

## 用户输入
{user_input}

## 示例
用户: 我的订单到哪了
输出: {{"intent":"logistics.query","confidence":0.95,"entities":[{{"name":"order_id","value":null,"source":"context"}}],"reasoning":"用户询问物流状态"}}

用户: 这个东西不要了想退
输出: {{"intent":"refund.apply","confidence":0.88,"entities":[{{"name":"product_name","value":"这个东西","source":"extracted"}}],"reasoning":"用户表达退款意愿"}}
"""
```

**Prompt 管理策略**：

- Prompt 模板存储在 MySQL，支持版本管理，运行时从内存缓存读取
- Few-shot 示例按意图动态选取（每个意图 3-5 个典型样本），而非全量灌入
- 用户输入超过 500 字时截断，避免 Token 浪费

#### 2.2.2 实体抽取策略

采用 **LLM 抽取 + 规则校验** 双层策略：

```
用户输入 → LLM 抽取(粗抽取) → 规则校验(精校验) → 最终实体
```

| 实体类型 | 抽取方式 | 校验方式 |
|----------|----------|----------|
| Enum 枚举值 | LLM 抽取 → 枚举匹配 | 精确匹配枚举表 |
| 手机号 | LLM 抽取 | 正则 `^1[3-9]\d{9}$` |
| 地址 | LLM 抽取 → 结构化 | 省市区三级联动校验（调用地址库API） |
| 金额 | LLM 抽取 | 数值范围校验 + 精度校验（2位小数） |
| 订单号 | LLM 抽取 / 上下文推断 | 调用订单API校验存在性+归属 |

**上下文推断**：当实体在当前轮未抽取到时，按优先级从以下来源补充：
1. 当前会话已填槽位（`filled_slots`）
2. 历史对话中的指代消解（"这个订单" → 最近的 order_id）
3. 用户画像默认值（收货地址 → 默认地址）

#### 2.2.3 置信度计算

置信度由 LLM 直接输出（0-1），经后处理校准：

```python
def calibrate_confidence(raw_confidence: float, intent: str, context: dict) -> float:
    """校准 LLM 输出的置信度"""
    calibrated = raw_confidence

    # 1. 意图先验概率调整：闲聊意图天然低置信度容许
    if intent == "chitchat" and raw_confidence < 0.5:
        calibrated = max(raw_confidence, 0.5)  # 闲聊不低于0.5，避免误转人工

    # 2. 实体完整度加成：槽位越完整，意图越确定
    slot_fill_ratio = context.get("slot_fill_ratio", 0)
    if slot_fill_ratio > 0.5:
        calibrated = min(calibrated * 1.1, 1.0)

    # 3. 历史意图一致性：连续N轮同一意图时加成
    consecutive_same_intent = context.get("consecutive_same_intent", 0)
    if consecutive_same_intent >= 2:
        calibrated = min(calibrated * 1.05, 1.0)

    return round(calibrated, 4)
```

**置信度 → 路由映射**：

| 校准后置信度 | 处理方式 |
|-------------|----------|
| ≥ 0.85 | 直接进入 DM 槽位填充 |
| [0.7, 0.85) | DM 发起隐式确认 |
| [0.5, 0.7) | DM 发起显式澄清（候选意图快捷按钮） |
| < 0.5 | 直接转人工 |

### 2.3 对话管理器设计

#### 2.3.1 状态机定义

状态机采用 **有限状态机 (FSM)** 模式实现，状态存储在 Redis：

```
状态定义: DialogState = Enum[
    INIT,              # 初始，等待用户输入
    INTENT_RECOGNIZED, # 意图已识别
    SLOT_FILLING,      # 槽位填充中
    READY_TO_EXECUTE,  # 槽位完整，待风控决策
    WAITING_CONFIRM,   # 等待用户确认（L2场景）
    EXECUTING,         # 技能执行中
    EXECUTED,          # 执行完成
    COMPLETED,         # 对话结束
    HUMAN_TAKEOVER,    # 转人工
    TIMEOUT,           # 超时
    CLOSED             # 会话关闭
]
```

**合法状态转换表**：

| 当前状态 | 允许转换 | 触发条件 |
|----------|----------|----------|
| INIT | INTENT_RECOGNIZED | NLU 返回意图 |
| INIT | HUMAN_TAKEOVER | 置信度 < 0.5 |
| INTENT_RECOGNIZED | SLOT_FILLING | 存在未填充的必填槽位 |
| INTENT_RECOGNIZED | READY_TO_EXECUTE | 所有必填槽位已填充 |
| SLOT_FILLING | SLOT_FILLING | 用户补充槽位（仍不完整） |
| SLOT_FILLING | READY_TO_EXECUTE | 所有必填槽位填充完成 |
| SLOT_FILLING | INTENT_RECOGNIZED | 用户意图切换 |
| READY_TO_EXECUTE | WAITING_CONFIRM | 风控路由为 CONFIRM_EXECUTE |
| READY_TO_EXECUTE | EXECUTING | 风控路由为 AUTO_EXECUTE |
| READY_TO_EXECUTE | HUMAN_TAKEOVER | 风控路由为 HUMAN_TAKEOVER |
| WAITING_CONFIRM | EXECUTING | 用户确认 |
| WAITING_CONFIRM | COMPLETED | 用户拒绝 |
| EXECUTING | EXECUTED | 技能执行完成 |
| EXECUTING | HUMAN_TAKEOVER | 执行超时/异常 |
| EXECUTED | COMPLETED | 结果已回复用户 |
| 任意 | HUMAN_TAKEOVER | 转人工触发 |
| 任意 | TIMEOUT | 超时 |
| TIMEOUT | CLOSED | 关闭 |

**实现**：使用 Spring Statemachine（Java 后端）管理状态流转，状态机实例与会话绑定，序列化到 Redis Hash 的 `dialog_state` 字段。非法转换抛出 `InvalidTransition` 异常，记录审计日志并回退到安全状态（转人工）。

#### 2.3.2 槽位填充流程

```
                    ┌─────────────┐
                    │  NLU 输出    │
                    │ intent+entities│
                    └──────┬──────┘
                           ▼
               ┌───────────────────────┐
               │  加载技能槽位定义       │
               │  (required_slots +    │
               │   optional_slots)     │
               └───────────┬───────────┘
                           ▼
               ┌───────────────────────┐
               │  合并：NLU抽取 + 上下文 │
               │  推断 + 默认值         │
               └───────────┬───────────┘
                           ▼
                  ┌────────────────┐
            ┌─No──│ 必填槽位全满？  │
            │     └───────┬────────┘
            │             │ Yes
            ▼             ▼
     追问缺失槽位     校验已填槽位
     (按优先级逐一)        │
            │        ┌────┴────┐
            │       No        Yes
            │        │         │
            ▼        ▼         ▼
        生成追问    提示校验   进入
        话术+按钮   失败原因   READY_TO_EXECUTE
```

**追问策略实现**：

```java
public class SlotFillingStrategy {

    /**
     * 生成槽位追问消息
     */
    public ClarificationMessage generateClarification(SlotDefinition missingSlot, DialogContext context) {
        String template = missingSlot.getClarificationTemplate();

        // 如果是枚举类型，生成快捷按钮
        if ("enum".equals(missingSlot.getType())) {
            List<String> options = missingSlot.getEnumValues().subList(0, Math.min(3, missingSlot.getEnumValues().size()));
            return ClarificationMessage.builder()
                .text(template)
                .type("action")
                .actions(options.stream()
                    .map(v -> QuickAction.of(v, v))
                    .collect(Collectors.toList()))
                .build();
        }

        // 如果有关联上下文可推断，给出确认
        String inferred = tryInferFromContext(missingSlot, context);
        if (inferred != null) {
            return ClarificationMessage.builder()
                .text(template + "（我猜是：" + inferred + "，对吗？）")
                .type("action")
                .actions(Arrays.asList(
                    QuickAction.of("是的", inferred),
                    QuickAction.of("不是", "__other__")))
                .build();
        }

        return ClarificationMessage.builder().text(template).type("text").build();
    }
}
```

#### 2.3.3 上下文管理策略

**上下文结构**（Redis Hash，key: `session:{session_id}`）：

| Redis Field | 类型 | 说明 | TTL |
|-------------|------|------|-----|
| `meta` | Hash | user_id, channel, created_at 等 | 30min（续期） |
| `state` | String | 当前对话状态枚举值 | 同上 |
| `intent` | String | 当前意图编码 | 同上 |
| `slots` | JSON String | 已填充槽位 Map | 同上 |
| `turns` | List | 最近20轮对话记录 | 同上 |
| `risk` | JSON String | risk_level + route_decision | 同上 |
| `emotion` | String | 情绪状态 | 同上 |

**指代消解**：在 NLU 阶段注入上下文信息，由 LLM 直接完成指代消解。例如用户说"这个订单"，LLM 在 `entities` 输出中填入上下文中的 `order_id`，`source` 标记为 `context`。

**意图切换**：检测到意图变化时：
1. 保留 `turns`（对话历史不丢失）
2. 清空 `slots`（旧意图槽位无效）
3. 重置 `state` 为 `INTENT_RECOGNIZED`
4. 保留 `emotion`（情绪状态不回退）

### 2.4 技能编排引擎设计

#### 2.4.1 技能注册机制

技能定义存储在 MySQL `skill_registry` 表，运行时加载到内存缓存（本地 Caffeine Cache + Redis 二级缓存），支持热更新：

```
MySQL skill_registry
    ↓ 启动时全量加载 + 变更时增量推送（RocketMQ）
Redis skill_cache:{skill_id}  (TTL=10min)
    ↓ 本地读取
Caffeine Cache (TTL=5min, max=200)
```

**技能注册数据结构**（JSON Schema 约束）：

```json
{
  "skill_id": "order_modify_address",
  "intent": "order.modify_address",
  "base_risk_level": "L1",
  "required_slots": ["order_id", "address_detail", "phone_number"],
  "optional_slots": ["consignee_name"],
  "api_chain": [
    {
      "step": 1,
      "api": "/api/order/query",
      "method": "GET",
      "params_mapping": {"order_id": "slots.order_id"},
      "purpose": "query_order_status",
      "required": true
    },
    {
      "step": 2,
      "api": "/api/order/modifyAddress",
      "method": "POST",
      "params_mapping": {
        "orderId": "slots.order_id",
        "address": "slots.address_detail",
        "phone": "slots.phone_number"
      },
      "purpose": "execute_modify",
      "required": true,
      "rollback_api": "/api/order/rollbackAddressModify",
      "rollback_params_mapping": {"modifyRequestId": "$.step1.response.modify_request_id"}
    }
  ],
  "pre_conditions": [
    {"field": "order.status", "op": "ne", "value": "signed"},
    {"field": "order.userId", "op": "eq", "value": "$.session.user_id"}
  ],
  "timeout_ms": 30000,
  "retry_policy": {"max_retries": 1, "backoff_ms": 1000},
  "enabled": true,
  "version": "1.2.0"
}
```

#### 2.4.2 API 调用链编排

API 调用链按步骤顺序执行，每步结果注入下一步的参数上下文：

```
步骤1执行 → 结果写入 $context.step1 → 步骤2参数映射从 $context 取值 → 执行步骤2 → ...
```

**参数映射表达式**：使用 JSONPath 语法，支持：
- `slots.order_id`：从槽位取值
- `$.step1.response.modify_request_id`：从上一步响应取值
- `$.session.user_id`：从会话上下文取值
- `$now`：当前时间戳
- `$uuid`：生成UUID

**错误处理矩阵**：

| 步骤结果 | 后续动作 |
|----------|----------|
| 成功 | 继续下一步 |
| 业务错误（2001/2002） | 中止链路，返回业务错误消息给用户 |
| 参数错误（1001） | 中止链路，记录异常，转人工 |
| 超时（3004） | 按重试策略重试，仍失败则中止 + 告警 |
| 服务不可用（3002） | 中止链路，转人工 + 告警 |
| 任意步骤失败且有 rollback_api | 逆序执行已成功步骤的回滚API |

#### 2.4.3 动态风险评估流程

```
意图识别完成(初步评估)
        │
        ▼
  ┌─────────────────────┐
  │ Step1: 基础风险评估   │  ← 查 skill_registry.base_risk_level
  └──────────┬──────────┘
             ▼
  ┌─────────────────────┐
  │ Step2: 业务状态查询   │  ← 调用 api_chain[0] 查询业务状态
  │   (订单是否发货等)    │     如: /api/order/status
  └──────────┬──────────┘
             ▼
  ┌─────────────────────┐
  │ Step3: 动态等级调整   │  ← 匹配动态风险评估规则表
  │   (已发货→L1升L2)    │     order.modify_address + 已发货 → L2
  └──────────┬──────────┘
             ▼
  ┌─────────────────────┐
  │ Step4: 风控规则叠加   │  ← 执行风控规则引擎(R001-R007)
  │   (频率/金额/情绪等)  │     取最高路由级别（只升不降）
  └──────────┬──────────┘
             ▼
  ┌─────────────────────┐
  │ Step5: 输出最终路由   │  → AUTO_EXECUTE / CONFIRM_EXECUTE /
  │   决策               │    HUMAN_REVIEW / HUMAN_TAKEOVER
  └─────────────────────┘
```

**关键实现**：Step2 的业务状态查询复用 api_chain 的第一步，避免重复 API 调用。查询结果缓存在会话上下文中，技能执行时不再重复查询。

**执行前二次校验**：在技能正式执行前（状态从 `WAITING_CONFIRM` → `EXECUTING`），重新查询业务状态，若状态已变更导致风险升级，中止执行并升级路由。

### 2.5 风控路由设计

#### 2.5.1 四级路由决策树

```
输入: intent + slots + user_context + emotion
        │
        ▼
```

#### 2.5.2 风控规则引擎

采用 **前向链式推理** 实现，规则配置化存储：

**规则存储**（MySQL `risk_rule` 表）：

```sql
CREATE TABLE risk_rule (
    rule_id      VARCHAR(16) PRIMARY KEY,
    rule_name    VARCHAR(64) NOT NULL,
    condition_expr TEXT NOT NULL,       -- SpEL表达式
    action       VARCHAR(32) NOT NULL,  -- UPGRADE_TO_REVIEW / UPGRADE_TO_TAKEOVER / NOTIFY_SUPERVISOR
    priority     INT NOT NULL DEFAULT 0,
    enabled      TINYINT(1) DEFAULT 1,
    phase        TINYINT NOT NULL,      -- 1=MVP, 2=扩展, 3=优化
    created_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

**规则执行**：使用 Spring Expression Language (SpEL) 作为条件表达式引擎，输入上下文 Map 包含：`user_id`、`intent`、`slots`、`emotion`、`frequency_count`、`refund_amount`、`user_register_days` 等。按优先级排序执行，命中即记录。

**频率计数实现**：

```
Redis Key: freq:{user_id}:{intent}
Value: 计数器
TTL: 3600s (1小时滑动窗口)

每次操作: INCR freq:{user_id}:{intent}
         EXPIRE freq:{user_id}:{intent} 3600  (仅当key不存在时设置)
```

| 故障场景 | 降级方案 | 用户感知 |

**工单分配引擎**：

```java
@Service
public class TicketAssignService {

    /**
     * 分配工单给坐席
     */
    public String assignTicket(Ticket ticket) {
        String intentGroup = getIntentGroup(ticket.getIntent());
        String onlineKey = "agent_pool:" + intentGroup + ":ONLINE";

        // 1. 查询同技能组在线空闲坐席
        Set<String> onlineAgents = redisTemplate.opsForSet().members(onlineKey);

        if (onlineAgents == null || onlineAgents.isEmpty()) {
            // 无空闲坐席，入待分配队列
            redisTemplate.opsForZSet().add(
                "ticket_queue:" + intentGroup,
                ticket.getTicketId(),
                ticket.getSlaDeadline().toEpochSecond(java.time.ZoneOffset.UTC));
            return null;
        }

        // 2. 轮询分配：取上次分配的下一个坐席
        String lastKey = "agent_pool:" + intentGroup + ":last_assigned";
        String lastAssigned = redisTemplate.opsForValue().get(lastKey);
        List<String> agentList = new ArrayList<>(onlineAgents);
        Collections.sort(agentList);

        int idx = 0;
        if (lastAssigned != null && agentList.contains(lastAssigned)) {
            idx = (agentList.indexOf(lastAssigned) + 1) % agentList.size();
        }

        String assignedAgent = agentList.get(idx);

        // 3. 更新坐席状态 → BUSY
        String busyKey = "agent_pool:" + intentGroup + ":BUSY";
        redisTemplate.opsForSet().remove(onlineKey, assignedAgent);
        redisTemplate.opsForSet().add(busyKey, assignedAgent);
        redisTemplate.opsForValue().set(lastKey, assignedAgent);

        return assignedAgent;
    }
}
```

#### 2.7.3 实时数据接口

实时数据不走 RAG，通过 API 网关直接调用电商业务 API：

| 数据 | API | 缓存策略 | 降级 |
|------|-----|----------|------|
| 库存 | `/api/product/stock` | 本地缓存 5min | 返回"暂无法查询" |
| 价格 | `/api/product/price` | 不缓存 | 返回"暂无法查询" |
| 物流 | `/api/logistics/track` | 本地缓存 1min | 返回"暂无法查询" |
| 订单状态 | `/api/order/status` | 不缓存 | 转人工 |
| 优惠信息 | `/api/promotion/active` | 本地缓存 10min | 跳过优惠信息 |

**原则**：涉及金额的数据绝不缓存，保证实时性；API 调用失败不使用过期缓存数据。

## 4. 关键接口设计

### 4.1 Agent 与业务 API 交互协议

**通用请求头**：

```http
Content-Type: application/json
X-Trace-Id: {全局唯一trace_id}
X-Request-Id: {请求唯一ID}
X-Idempotency-Key: {幂等键，写操作必填}
Authorization: Bearer {service_token}
X-Source: smartcs-agent
X-Timestamp: {epoch_millis}
X-Signature: HmacSHA256({method}{path}{body}{timestamp}, secret_key)
```

**签名算法**：`HmacSHA256(method + "\n" + path + "\n" + body + "\n" + timestamp, secret_key)`

**统一响应**：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "trace_id": "trace_xxx",
  "timestamp": 1720000000
}
```

**幂等性保障**：写操作必须携带 `X-Idempotency-Key`，业务端基于此键去重。相同 Idempotency-Key 的重复请求返回首次执行结果。

**超时与重试**：

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 连接超时 | 5s | TCP 连接建立超时 |
| 读取超时 | 25s | 等待响应超时 |
| 最大重试 | 1次 | 仅对 3001(系统繁忙) 和 3004(超时) 重试 |
| 退避策略 | 指数退避 | 1s → 2s |
| 重试条件 | 响应码 3001/3004 或网络异常 | 业务错误不重试 |

### 4.2 内部模块间通信方式

| 通信场景 | 方式 | 理由 |
|----------|------|------|
| 网关 → Agent Core（用户请求） | gRPC 同步 | 低延迟，请求-响应模式 |
| Agent Core → 网关（回复推送） | RocketMQ 异步 | 解耦，支持多消费端 |
| Agent Core → 后端服务（API调用） | HTTP 同步 | 标准化，与业务系统协议一致 |
| 工单创建 → 坐席推送 | RocketMQ → WebSocket | 异步解耦 + 实时推送 |
| 技能执行结果 → 通知服务 | RocketMQ 异步 | 非阻塞，通知可重试 |
| 风控规则变更 → Agent Core | RocketMQ 广播 | 配置热更新，所有实例同步 |
| 会话状态变更 → 监控 | RocketMQ 异步 | 非关键路径，不阻塞主流程 |

**gRPC 接口定义（网关 → Agent Core）**：

```protobuf
service AgentService {
  // 处理用户消息（同步，流式响应）
  rpc ProcessMessage(MessageRequest) returns (stream MessageResponse);

  // 查询会话状态
  rpc GetSessionState(SessionQuery) returns (SessionState);

  // 用户确认操作
  rpc ConfirmAction(ConfirmRequest) returns (ConfirmResponse);
}

message MessageRequest {
  string session_id = 1;
  string user_id = 2;
  string channel = 3;
  string message_type = 4;  // text/image/action
  string content = 5;
  map<string, string> context = 6;
}

message MessageResponse {
  string message_id = 1;
  string message_type = 2;  // text/card/action
  string content = 3;
  repeated QuickAction actions = 4;
  string dialog_state = 5;
}

message QuickAction {
  string label = 1;
  string value = 2;
  string action_type = 3;  // confirm/select/cancel
}
```

### 4.3 WebSocket 推送方案

**用户端 WebSocket**：

```
连接: ws://gateway/ws/user?token={jwt_token}
鉴权: 连接时校验 JWT，失败关闭连接
心跳: 客户端 30s ping → 服务端 pong，超时 60s 断开
重连: 客户端指数退避重连(1s/2s/4s/8s/max30s)
消息格式: {"type":"message|state|notification","data":{...}}
```

**坐席端 WebSocket**：

```
连接: ws://gateway/ws/agent?token={jwt_token}
鉴权: 连接时校验 JWT + 坐席角色
心跳: 同用户端
推送事件:
  - ticket_assigned: 新工单分配
  - ticket_escalated: 工单升级
  - ticket_sla_warning: SLA 即将超时
  - supervisor_approval: 主管审批请求
  - user_message: 用户新消息（接管对话后）
```

**消息推送可靠性**：

1. 发送端：消息先写 Redis 队列，再推送 WebSocket；推送失败则保留在队列
2. 接收端：重连后拉取离线消息（`GET /api/messages/offline`）
3. 消息 ID 递增，客户端去重

### 6.2 容量规划建议

| 组件 | 规格 | 数量 | 说明 |
|------|------|------|------|
| Gateway Pod | 2C4G | 6 | 支撑 500 QPS |
| Agent Core Pod | 4C8G + GPU(T4) | 4 | LLM 推理用 GPU，2 实例备用 |
| Backend Pod | 4C8G | 3 | 业务 API 调用 |
| MySQL | 8C32G SSD | 1主2从 | 审计日志按月分表 |
| Redis Cluster | 8C16G | 6节点(3主3从) | 会话状态+限流+缓存 |
| Milvus | 8C16G | 4节点 | 10万级知识向量 |
| ES | 8C32G SSD | 6节点 | 日志+知识检索 |
| RocketMQ | 4C8G SSD | 6节点 | 异步消息 |

**存储估算**：
- 对话数据：日均 50 万轮 × 1KB ≈ 500MB/天，月增量 ~15GB
- 审计日志：日均 100 万条 × 2KB ≈ 2GB/天，月增量 ~60GB
- 知识向量：10 万 chunk × 4KB ≈ 400MB（较小）

### 6.3 高可用方案

| 组件 | HA 方案 | RTO | RPO |
|------|---------|-----|-----|
| Gateway | K8s Deployment 多副本 + HPA | < 30s | 0 |
| Agent Core | K8s Deployment 多副本 + 就绪探针 | < 60s | 0 (无状态) |
| Backend | K8s Deployment 多副本 | < 30s | 0 |
| MySQL | 主从半同步复制 + 自动故障转移 (MHA/Orchestrator) | < 60s | < 1s |
| Redis | Cluster 模式 + Sentinel 自动故障转移 | < 30s | < 1s |
| RocketMQ | 多 Master 多 Slave + Dledger 自动选主 | < 30s | < 1s |
| Milvus | Cluster 模式 + 副本 | < 60s | 0 |
| ES | 副本分片 + 自动平衡 | < 60s | 0 |

**多可用区部署**：K8s Node 分布在 2 个可用区，Pod 反亲和调度确保同一服务不同副本分布在不同可用区。

**灾备**：MySQL 每日全量备份 + 实时 Binlog 归档至 OSS，支持跨区域恢复。Redis 开启 AOF 持久化。

## 7. 技术选型说明

### 7.1 LLM 选型

| 选项 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| **Qwen-Max** (选中) | 中文能力最强；国内部署合规；延迟低 | 生态略弱于 OpenAI | ✅ 主力模型 |
| GPT-4o | 综合能力强；生态成熟 | 国内合规风险；延迟高 | 备选降级模型 |
| Qwen-Plus | 成本低；速度快 | 能力弱于 Max | 低风险场景降级用 |
| 规则引擎 | 零延迟；100%可控 | 灵活性差 | LLM 全不可用时的兜底 |

**降级链路**：Qwen-Max → GPT-4o → Qwen-Plus → 规则引擎 → 转人工

### 7.2 向量库选型

| 选项 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| **Milvus** (选中) | 开源成熟；支持集群；云原生；过滤+向量混合查询 | 运维复杂度较高 | ✅ 推荐 |
| Weaviate | 内置向量化；GraphQL API | 社区较小；性能不及 Milvus | 备选 |
| Pinecone | 全托管；零运维 | 闭源；国内合规风险 | 不适用 |

### 7.3 消息队列选型

| 选项 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| **RocketMQ** (选中) | 国内生态成熟；事务消息支持好；可靠性高 | 社区国际化弱 | ✅ 推荐 |
| Kafka | 吞吐量极高；国际生态好 | 运维复杂；事务支持弱 | 备选（已有Kafka集群时） |
| RabbitMQ | 轻量；易上手 | 吞吐量不足；消息积压能力弱 | 不适用 |

### 7.4 前端框架选型

| 选项 | 决策 | 理由 |
|------|------|------|
| **React 18** (坐席工作台) | ✅ 选中 | Ant Design Pro 生态成熟；坐席后台标准选型 |
| **Vue 3** (用户端 H5) | ✅ 选中 | 体积小、性能好；H5 嵌入场景友好 |
| —— | 两套并存 | 坐席端用 React 享受 ProComponents；用户端用 Vue 保证轻量 |

### 7.5 Agent 核心语言选型

| 选项 | 优势 | 劣势 | 决策 |
|------|------|------|------|
| **Python** (选中) | LLM 生态最强(LangChain/LlamaIndex)；开发效率高 | 性能弱于 Go/Java；GIL | ✅ Agent 核心层 |
| Java | 性能强；与后端统一 | LLM 生态弱 | 后端支撑层 |
| Go | 高并发；低资源 | LLM 生态弱 | 不适用 |

### 7.6 状态机实现选型

| 选项 | 决策 | 理由 |
|------|------|------|
| **Spring Statemachine** | ✅ 选中 | 与 Spring Boot 深度集成；支持持久化到 Redis；可视化状态图 |
| 自研 FSM | 备选 | Statemachine 不满足时 |
| Python transitions | 不适用 | Agent 核心如用 Python 实现时选用 |
